# DischargeFlow: explain the code part by part

## 1. The whole system in one explanation

“The browser shows separate coordinator and patient interfaces. It sends requests to our server. The server verifies the signed-in account and its permissions, validates the requested action, then reads or updates the shared database. The simulator takes a copy of the current backlog and compares scenarios without updating patient tasks.”

Follow this path:

**Browser → API route → authentication/validation → database or simulator → JSON response → updated screen.**

HTML defines page content, CSS controls appearance, JavaScript handles interactions and business rules, TypeScript connects the framework and defines schema, and SQL stores/queries records. JSON is the format exchanged between browser and server. An API is the agreed set of requests connecting those two parts.

## 2. Browser interface: `public/app.js`

This is the main product interface. Read it by function, not as one large block.

| Function / section | What it does | What to explain |
|---|---|---|
| `api()` | Sends a request and reads the JSON response; adds the CSRF token and handles errors. | One shared request helper avoids repeating connection/error code. |
| `login()` | Shows the login form and submits an ID/email plus password. | A successful server response selects the appropriate workspace. |
| `shell()` | Draws the common heading, account controls and coordinator sidebar/mobile menu. | Shared navigation keeps separate pages consistent. |
| `tasksMarkup()` | Builds the discharge progress timeline. | Patients get plain descriptions; staff see task owners and controls. |
| `dashboard()` | Loads active cases or the linked patient admission. | Search and filters act on the coordinator's fetched list. A patient list of all cases is never sent. |
| Nested `openCase()` | Opens a case dialog, task actions, history, receipt form and departure action. | The server checks whether the requested action is allowed. |
| `newCaseForm()` | Collects a new admission and medical-clearance details. | The app records staff input; it does not decide medical fitness. |
| `coordinatorPage()` | Chooses the appropriate separate coordinator screen. | There are distinct URLs rather than one elongated dashboard. |
| `patientAccessPage()` | Creates linked accounts and manages credential reissue/revocation. | Patient data access is deliberately granted to a particular admission. |
| `changePasswordPage()` | Replaces a temporary credential before case access. | Issuing an account and activating it are separate steps. |
| `helpDesk()` | Displays saved messages and lets a coordinator reply. | This is human support, with no guaranteed response time. |
| `patientAssistant()` | Displays the chatbot transcript and sends questions. | Its answers are generated by rules on the server, not an AI model. |
| `operationalAlerts()` | Shows rule explanations and department queue categories. | Elapsed, queued, processing, blocked, held and external waiting mean different things. |
| `simulator()` / `simulationResults()` | Collect assumptions and draw baseline/scenario comparisons. | Results are estimates under stated assumptions. |
| `insurancePanel()` / `bindInsuranceReceipt()` | Show verified receipt timing and the staff receipt-entry form. | Patient notices refresh every 30 seconds while the page is open; no SMS/email is implemented. |
| `esc()` | Escapes text before placing it in generated HTML. | Patient/staff input must not become executable HTML. |

`let` declares values that may change; `const` fixes a reference; functions group operations; `async`/`await` let requests finish without freezing the page. `.map()` transforms records into display elements; `.filter()` selects matching records. Template strings combine HTML with escaped values. Event handlers run when someone clicks or submits.

**Important:** hiding a button is a usability choice, not security. The server must reject unauthorised API calls even if someone bypasses the interface.

## 3. Appearance and HTML shell

- `public/styles.css`: colours, spacing, typography, tables, timeline, dialogs, sidebar, responsive mobile layout, chart and insurance notice styling.
- `public/favicon.svg`: browser tab icon.
- `app/lib/assets.js`: initial HTML document and links to the browser script/styles. Most visible page content is inserted by `public/app.js`.

## 4. Entry point: `app/[...path]/route.ts`

The catch-all route forwards GET and POST requests to `handle(request, env)`. GET usually reads a page/data; POST submits an action. `env` supplies the database binding and server-held bootstrap secret. The route is dynamic because responses depend on the account and stored data.

`worker/index.ts` is the hosting entry point: it passes incoming requests into Vinext's handler. Its connector support is retained platform infrastructure; it is not a hospital integration.

## 5. Main server: `app/lib/backend.js`

`handle()` is the main request dispatcher. Explain it in this order:

1. **Response helpers:** consistent JSON responses, redirects, security headers and error responses.
2. **Database helpers:** `get` reads one row, `all` reads multiple rows, `run` changes data and `batch` groups changes atomically. Values are bound to SQL parameters rather than concatenated into SQL.
3. **First-run bootstrap:** creates the original fictional accounts/cases when the database is empty, using a server-configured password. It hashes passwords with a random salt and PBKDF2-SHA256, using 100,000 iterations. Existing passwords are not reset by later bootstrap configuration changes.
4. **Login/session:** checks the stored salted hash, applies failed-login limits, issues an HttpOnly/Secure/SameSite cookie and stores a hash of its random session token. Sessions last 30 minutes. A CSRF token is required for authenticated writes. Logout removes the session.
5. **Permissions:** coordinator-only routes reject patient accounts. The patient route selects its admission through the server's account-to-case mapping, ignoring attempts to choose another case through URL input.
6. **Case creation:** validates admission details and creates the five tasks. Insurance is marked not required for self-pay.
7. **Workflow actions:** start/complete/hold/resume checks task state and prerequisites. A hold retains its prior working state separately. The request includes the last seen timestamp so a stale update does not silently overwrite a newer one.
8. **History/departure:** records who acted, what changed and when. All tasks being complete is distinct from staff recording actual departure. Previous cases remain saved.
9. **Support:** keeps saved help threads separate from transient chatbot conversations.
10. **Alerts:** calculates transparent thresholds; a stale status warns about missing updates, not proof that no work happened. Insurance final-authorisation uses its own receipt-based threshold.
11. **Simulation:** validates numeric assumptions and snapshots active tasks, then invokes `simulate()` twice. It writes no case/task changes.
12. **Mock hospital events:** accepts supported fictional events, checks workflow order and uses event IDs to avoid applying duplicates twice. It is not connected to a real hospital.

Security here is prototype functionality, not a claim of hospital production readiness. Production would require hospital identity integration, reviewed permissions, operational monitoring, backup/recovery, security testing and appropriate data governance.

## 6. Accounts: `app/lib/accounts.js`

This module handles the patient/relative account lifecycle. A coordinator chooses an existing active admission, records identity/authorisation attestations and creates an account with patient-level permissions. The checkboxes record staff confirmation; they are not automated identity verification.

A random temporary password is returned once, expires in two hours and must be replaced before case data can be read. Only its salted hash is stored. New IDs use PAT-/REL- plus a numeric user ID. Credential reissue ends existing sessions; revocation removes admission access and sessions immediately. Accounts cannot silently be relinked to another admission. Live prototype credentials are not committed to source.

## 7. Database: `db/schema.ts` and `drizzle/`

The schema describes the tables; migrations create/update them. A migration is a versioned database change, applied once. `db/index.ts` is a retained Drizzle helper; the main backend uses prepared D1 SQL directly.

| Tables | Purpose |
|---|---|
| `users`, `login_aliases` | Account identity, role, password hash and alternative login IDs. |
| `sessions`, `login_attempts` | Signed-in sessions and failed-login counters. |
| `cases`, `case_clearance` | Admission, ward, payment pathway and recorded medical-clearance information. |
| `tasks`, `task_holds`, `task_events` | Current stage states, hold reasons and change history. |
| `access`, `account_access` | Which admission a person may view and how access was provisioned/revoked. |
| `departures` | Actual departure records retained for Previous cases. |
| `help_threads`, `help_messages` | Saved patient/coordinator conversations. |
| `alert_settings`, `assistant_limits` | Demo thresholds and chatbot request counters. |
| `insurance_receipts` | Verified insurer receipt timestamp, acknowledgement, insurer and recording staff. |
| `sample_batches` | Prevents reseeding the same fictional cohort. |
| `mock_events` | Tracks incoming mock event IDs to prevent duplicates. |
| `audit` | Account/security activity records. |

There is no single `database.json`. The hosted database is persistent Cloudflare D1; local preview uses separate SQLite-backed state under ignored `.wrangler/state`. Source includes schema and fictional seed logic, not a live database dump.

## 8. Sample data: `app/lib/samples.js`

Adds 30 synthetic admissions with varied stages and payment pathways. Five have recorded departures. It adds professional-looking ID/email aliases for the original three accounts. An atomic seed batch plus version marker makes it safe to open Active cases again without creating another cohort. It preserves existing records/passwords. More samples improve the demonstration; they do not validate a predictive model.

## 9. Simulator: `app/lib/model.js`

This is a **deterministic discrete-event simulator**, not trained predictive AI. Deterministic means the same cases and inputs produce the same result. Discrete-event means it advances to the next task completion or assumed hold release rather than simulating every second.

1. Copy cases into simulation jobs and classify tasks as done, pending, running, held or awaiting an external insurer response.
2. Set available operators for each stage. Already running tasks use capacity immediately and their entered duration is assumed remaining work.
3. Check dependencies: documentation and pharmacy may run in parallel; billing waits for both; insurance follows billing; final checks wait for applicable stages.
4. Queue eligible tasks reproducibly by future eligibility and tie-breaking order. Assign work only while an operator is available.
5. Schedule service completion events. Internal insurance-desk work is separate from external insurer waiting; extra internal operators do not accelerate an external response. An already received request starts in external waiting.
6. Advance to the next event, release capacity and repeat until tracked tasks finish.
7. Return per-case remaining time, average, 90th percentile, ready-by-cutoff count and queue-wait summaries.
8. The API runs baseline and scenario on the same snapshot, changing one department's capacity. The UI displays both and their differences.

Example: two billing tasks requiring 30 minutes each can use one operator sequentially or two in parallel. Overall discharge improvement may be smaller if insurance or another dependency still dominates. No improvement is a legitimate result.

Limitations: fixed backlog, no new arrivals, no shifts/breaks, assumed service/hold/insurer durations, no calibrated uncertainty range. Outputs measure remaining tracked-workflow time, not medical fitness, authorised departure or bed availability. A validated digital twin would require operational calibration and validation; historical-data prediction is future work.

## 10. Chatbot: `app/lib/assistant.js`

Recognises supported questions and returns explanations or progress for the authenticated person's linked case. It refuses to promise a departure time, redirects medical/urgent issues to ward staff and offers human help for unsupported questions. It does not call an LLM, train on messages, diagnose or approve claims. The server also handles receipt-based insurance-rights questions.

## 11. Insurance: `app/lib/insurance.js`

Separates the insurer's verified receipt of the final cashless discharge request from medical clearance. The three-hour notice activates only beyond 180 minutes, and authorisation completion stops its clock. No verified receipt means “unverified,” not an invented delay. Correcting receipt data requires a reason and stale-update check. Information is sourced in the UI; it does not calculate compensation, approve claims or guarantee cash benefits. Current notification delivery is an on-page notice while the patient view is open.

## 13. Likely code questions and honest answers

**Did your team write every line?** “We used AI-assisted development and a retained framework starter. We can explain the application flow and have tested these features. We will follow the event's disclosure rules.” Add each member's actual contribution; do not invent work.

**Why is a patient unable to view another case?** “The server resolves the case from the account mapping; a browser-selected ID is not trusted.”

**Are passwords saved as text?** “No. Salted PBKDF2 hashes are stored. Temporary passwords are only shown on issue/reissue.”

**Can two coordinators overwrite each other?** “Task writes include the last seen timestamp. A conflicting update is rejected and must be refreshed.”

**Where is AI?** “There is no trained predictive AI yet. Alerts and chatbot are rules-based; simulation uses explicit assumptions.”

**How do you know adding staff helps?** “We compare the same synthetic backlog under two capacities. It is an estimate; hospital benefit requires a pilot and validation.”

**Can this work without hospital integration?** “A supervised standalone pilot can use manual entries. That creates staff effort; the prototype demonstrates mock events only. Production integration needs vendor APIs, permissions and reconciliation.”

**Why another app?** “It must reduce coordination effort. We should integrate existing events and avoid duplicate entry; staff interviews and a pilot must test that value.”

**Does it exist already?** “Digital discharge tracking and prediction already exist. Our proposed focus is lightweight coordination and transparent operational scenario comparison; we do not claim unique invention.”

**Is this NHCX?** “No. It does not exchange live insurance claims through NHCX. A cashless status tracker and hospital workflow simulator have a different role.”

**What did you test?** “Role isolation, workflow prerequisites, account lifecycle, messages, simulation, sample seeding and receipt rules. These tests do not prove real-world wait reduction.”

**What happens when a patient leaves?** “Staff record departure separately. The case leaves Active cases and remains in Previous cases.”

**Is the entire website complete?** “It is a functional fictional-data prototype. Real integration, validated prediction, production governance and clinical deployment are outside the current build.”

## 15. New insurance, appointment and support modules

# Expanded workflows and code locations

## Insurance investigation

Coordinator > Insurance desk lists active insured cases. Staff can filter cases beyond the three-hour window, follow-ups due, or cases with no verified cause. The Alerts page also identifies approaching three-hour deadlines and missed follow-up times.

Open Investigate and follow up to:
1. Record or correct the verified insurer receipt and acknowledgement. Insurer queries never restart that original clock.
2. Record the operational stage: preparation, submitted, query received, response sent, escalated, final authorisation or rejection recorded.
3. Keep the cause unknown until staff verify evidence. Categories include documents, queries, bill/package mismatch, coverage review, external processing, technical issue and other.
4. Assign a responsible owner and next follow-up time. Add a clear patient-facing update.
5. Prepare an editable contact draft. Copying a draft sends nothing.
6. Use the hospital's approved phone/email/portal channel, then record the actual attempt, contacted party, reference and factual outcome. Staff-only contact notes do not appear in the patient view.

The patient sees the recorded stage, verified cause, owner, next follow-up and public update. This is an operational record, not automatic root-cause detection, live insurer status or claim adjudication. The app cannot compel approval, calculate compensation or guarantee faster discharge. Rejected cases require human insurance review. Real integration requires an approved insurer/hospital interface and governance.

Files: `public/app.js` (`insuranceDeskPage`, `patientInsuranceOps`), `app/lib/insurance-ops.js` (workflow/contact routes), `app/lib/insurance.js` (verified receipt timer), `app/lib/backend.js` (permissions and alerts). Tables: `insurance_workflows`, `insurance_contact_events`, existing `insurance_receipts`.

## Appointment coordination

The patient view has Follow-up appointments. A patient or authorised relative requests a department and preferred time for the linked admission. Requests are not confirmed bookings. Coordinators open Follow-up appointments, check hospital availability, and confirm a clinician, time and location, or decline with a reason. Patients can cancel their own open requests/appointments. A declined/cancelled request remains in history.

The prototype blocks the exact same confirmed start time for the same clinician and guards against stale updates. It does not model appointment duration, overlapping time ranges, staff rosters, real calendar availability, payment or notifications. This is for follow-up coordination of linked admissions, rather than public new-patient registration.

Files: `public/app.js` (`patientFollowup`, `appointmentPage`, `bindAppointmentActions`), `app/lib/followup.js`. Tables: `appointment_requests` and its partial unique indexes.

## Billing and patient support

The help desk lets a patient create distinct issues. Billing options cover itemised bills, unclear charges, possible duplicates, payment not reflected, deposit adjustment, refund status, packages/tariffs, pharmacy charges and co-pay/deductible clarification. Insurance, documents, appointments and discharge coordination have their own categories. Other accommodates issues outside the listed options; the list cannot enumerate every possible hospital issue.

Each ticket has a HELP ID, admission, requester, reference, description, owner, saved replies and a state: open, waiting for patient, billing review, insurance review or resolved. Only staff control the resolution state. A patient reply reopens an unresolved waiting issue as open. Resolved tickets remain readable; a recurring issue can be reported separately. Previous general conversations remain available under General messages and previous conversations.

Staff must verify charges and process any adjustment/refund outside this prototype. A resolved ticket means staff recorded a resolution; it is not proof that a bank transaction happened. Do not enter bank/card credentials or real clinical data. This is not an emergency channel.

Files: `public/app.js` (`helpDesk`, `generalHelpDesk`), `app/lib/support.js`. Tables: `support_tickets`, `support_replies`. Existing `help_threads` and `help_messages` remain preserved.

## Personal departure preparation

Patients can save personal checks for belongings, transport/assistance and questions for the hospital team. They do not complete hospital tasks or authorise departure. File: `app/lib/followup.js`; UI: `preparationPanel`; table: `case_preparations`.

## Review demonstration

1. Coordinator > Insurance desk > an overdue fictional admission. Show verified receipt, unknown cause, evidence requirement, owner/follow-up, draft and contact history.
2. Patient > request a follow-up visit. Coordinator > confirm actual fictional arrangements. Patient > refresh and view confirmation.
3. Patient > help desk > billing > possible duplicate charge. Coordinator > reply, assign billing review and record a resolution.
4. Simulator > compare a staffing scenario. Explain that outcomes use assumptions and that no predictive AI is trained.

Use fictional details. A demo contact record must be explicitly labelled fictional, not presented as evidence that an insurer was contacted.


## 16. OC challenge and credentials

# OC challenge: directory, appointments, attendance and history

## One staff person

The platform administrator manages hospital/doctor directory entries. Hospital coordinators see only their assigned hospital's admissions. Patients/relatives see only their linked admission. See HOSPITAL_ROLES.md for the current model. There is no public staff signup; the original coordinator login remains valid within Cedar Valley.

The original coordinator account is created in `app/lib/backend.js` when the database has no users. The initial password comes from the server-held `BOOTSTRAP_PASSWORD` setting and is stored as a salted PBKDF2 hash. `STAFF-000001` is a login alias for that account, created by the sample cohort in `app/lib/samples.js`. Initial names/emails/roles are synthetic bootstrap records. This is a prototype setup, not hospital HR verification or staff SSO.

Temporary patient/relative passwords serve a different purpose: handing a newly provisioned account to its verified owner. They expire after two hours and must be replaced before case access. They are not an SMS OTP. They may work until replaced/expired/reissued/revoked; the application does not promise that they can be used for only one login. Reissue ends existing sessions and replaces the credential. The patient chooses their own password, which staff cannot retrieve in readable form. Those rules are in `app/lib/accounts.js`.

## Hospital and doctor selection

A fictional directory contains four hospitals and twelve doctors. Only platform admins can create/edit hospital and doctor profiles and activate/deactivate entries under Hospitals and doctors. No hard deletion is available, preserving references from old appointments. Inactive hospitals and their doctors disappear from new patient selection lists. Being in the directory is not medical credential verification or live availability.

Patients choose a hospital, then a doctor belonging to that hospital, and request a preferred time. The server derives the specialty from the selected doctor and rejects inactive or mismatched selections. The coordinator checks availability externally before confirming a doctor, time and clinic. Doctor changes require an explanation. Existing requests from the earlier version remain visible and can receive directory selections at confirmation.

File map: `public/app.js` - `directoryPage`, `patientFollowup`, `appointmentPage`, `bindAppointmentActions`; `app/lib/directory.js` - seeding and admin management; `app/lib/followup.js` - appointment validation and writes. Tables: `hospitals`, `doctors`, `appointment_requests`, `appointment_events`.

## Missed appointments

A confirmed appointment whose time has passed is flagged as attendance needing review. The app does not assume the patient missed it. A coordinator must verify attendance, provide a factual note and mark it attended or missed. Future appointments cannot be marked missed/attended, and patients cannot set their own attendance status.

Patients can request another visit from a missed/cancelled/declined appointment. The app creates a new request linked by `rescheduled_from`, retaining the old outcome and event history. A new request still requires hospital confirmation. Patients cannot cancel a past confirmed visit to bypass staff attendance review.

The coordinator can explicitly load three fictional attendance examples once: one missed, one attended and one past confirmed visit awaiting review. They are labelled snapshots, not real observations. Earlier events are not fabricated. Existing appointments remain saved. The example action is coordinator-only and does not change login credentials.

The prototype prevents an exact duplicate confirmed start time for the same directory doctor. It does not model appointment length, overlapping time ranges, real rosters or hospital calendar availability.

## Case history

A coordinator can choose stored admissions belonging to their hospital; the platform admin can choose across hospitals under Case history. Patients can open only the admission linked to their account. The view combines clearance, recorded departure, current discharge stages, task events and linked appointment outcomes. Each appointment also has a separate event history.

This is operational case history, not an electronic medical record: no diagnoses, prescriptions or clinical test results are stored. Internal task-event notes do not appear in the patient's history. Contact-desk private notes are not included. Initial snapshots and older requests without events remain explicitly identified.

Files: `app/lib/case-history.js`; browser functions `caseHistoryPage`, `patientCaseHistory`, `caseHistoryMarkup`.

## Scope and presentation answers

- Admin access: a separate platform admin has cross-hospital oversight and directory administration.
- Doctor appointment: patient selection plus manual hospital confirmation.
- Missed appointment: staff-verified outcome, not an automatic assumption from elapsed time.
- Case history: admission-scoped operational timeline and appointment outcomes.
- Hospital lists: maintained fictional directory, not a real hospital integration.
- Credentials: original staff bootstrap and separate temporary patient-account handover.

Coordinators now have hospital-specific access, with cross-hospital oversight reserved for the platform admin. The prototype uses fictional assignments. Production use still requires credential verification, security review, governance and approved interfaces.
